# Service Layer and API

## 1. Every resource has its own service layer

A **resource** (user, group, role, kiosk, payment method, …) gets **one service module of its
own**, colocated with its feature and named after the resource:

```
modules/identity/src/features/user/
    userService.ts   ← the service layer  (HTTP only)
    commands.ts      ← command names + handler registration
    types.ts         ← request/response types
    index.ts
```

One resource → one service file. Never a shared `apiService.ts` handling several resources, and
never HTTP calls inline in a component or a hook.

### The three layers

```
component / hook
      │  publish({ name, payload })
      ▼
commands.ts       — names + bus.subscribe, one line per operation, no logic
      │  svc.searchUsers(payload)
      ▼
xService.ts       — the service layer: HTTP only, returns CommandResponse, never throws
      │  schema.restApi.search(request)  /  request.get(...)
      ▼
RestApi / RequestMaker (@nikkierp/common)
```

**The service layer is the only place that talks HTTP.** Components never call `request.*` and
never touch `RestApi` directly — they publish a command.

### Service function contract

- Named exports, function-declaration syntax, one per operation
  (`createUser`, `getUserById`, `searchUsers`, `updateUser`, `deleteUser`,
  `setUserIsArchived`, `userExists`).
- Signature: `(request: t.XRequest) => Promise<CommandResponse<t.XResponse, unknown>>`.
- **Never throws.** A rejected HTTP call becomes `{ data: null, error }`. This is what lets
  `commands.ts` be a flat list of one-line bindings.
- Aliased operations are fine when the backend has no dedicated endpoint —
  `activateUser` / `suspendUser` / `inviteUser` all delegate to `restApi.update`.

Because "never throws" would otherwise mean a `try/catch` in every function, each module has a
single helper that does the wrapping:

```ts
// identity — resolves the schema and wraps the outcome
async function withUserSchema<TData>(fn: (schema: dyn.SchemaPack) => Promise<TData>) {
    try { return ok(await dyn.withSchema(USER_SCHEMA_NAME, fn)); }
    catch (error) { return fail(error); }
}
```

```ts
// vendingMachine — @/common/commandBus/serviceResult.ts
export async function attempt<TData>(fn: () => Promise<TData>): ServiceResult<TData> {
    try { return ok(await fn()); }
    catch (error) { return fail(error); }
}
```

## 2. The standard REST API: `@nikkierp/common/dynamicModel/restapi.ts`

The backend implements **dynamic modelling**: every resource is exposed through the *same*
predictable endpoint set. The frontend mirrors that with **one shared `RestApi` class** —
`nikkierp/libs/common/src/dynamicModel/restapi.ts`. Service layers **must reuse it** rather than
re-writing `GET /v1/iam/users`-style calls by hand.

### Endpoints

| Method | HTTP | Path (relative to `resourcePath`) |
| --- | --- | --- |
| `getModelSchema()` | GET | `/meta/schema` |
| `search(req)` | GET | `/` — `fields`, `page`, `size`, `graph`, `language`, `search_name`, `org_id` |
| `getById(req)` | GET | `/{id}` |
| `getOne(req, buildParams)` | GET | `/getOne` — lookup by a non-id key |
| `exists(req)` | POST | `/exists` — `{ ids }` → `{ existing, not_existing }` |
| `create(req)` | POST | `/` → `{ id, etag, created_at }` |
| `update(req)` | PATCH | `/{id}` — body must carry `etag` |
| `delete(req)` | DELETE | `/{id}` |
| `setIsArchived(req)` | POST | `/{id}/archived` — `{ etag, is_archived }` |
| `manageM2m(req, path)` | POST | `/{path}` — `{ add: [], remove: [] }` |

Cross-cutting behaviour you get for free by reusing it:

- **Request de-duplication.** `getById`, `getOne`, `getModelSchema` and `search` compute a
  `dedupKey`; `RequestMaker` collapses identical in-flight requests into one.
- **Optimistic concurrency.** `update` / `setIsArchived` require an `etag`; mutations return a
  fresh one.
- **`search(size: 0)` short-circuits** to an empty result without hitting the network.
- **Search graph.** `graph` is a plain-JSON tree — `{ if: ['status', '=', 'active'] }`,
  `{ and: [...] }`, `{ or: [...] }`, `{ order: [['name','asc']] }` — with operators
  `= != > >= < <= * !* ^ !^ $ !$ in not_in is_set not_set linked not_linked`. `linked` /
  `not_linked` only apply to a many edge (the field is the edge name, the value a peer row id).
- **Nested resources.** Construct with `primaryResourcePath` and pass a `primaryResourceId`
  to get `/{primary}/{primaryId}/{resource}`.

### Org-scoped resources

Many backend resources are owned by an organization, and their search endpoints bind `org_id`
from a query param and fold it into the search graph **unconditionally**. The failure mode is
worth internalising: omitting `org_id` does not widen the query, it filters on the empty string
and returns **nothing**. An empty list is indistinguishable from "this org owns no records", so
the bug reads as missing data rather than as a missing parameter.

Pass it on `search` (and `getById`, where the resource is org-owned). `org_id` is part of
`search`'s `dedupKey`, so two organizations asking for the same page never collide in the
de-duplication map.

The org id comes from the Shell over the command bus — see §3.7 of
[Micro Frontend architecture](<./01. Micro Frontend architecture.md>). A module whose resources
are *all* org-scoped should fold it in once, in a base service, rather than in each service or
hook:

```ts
// coremart/modules/vendingMachine/src/common/service/OrgScopedCrudService.ts
export abstract class OrgScopedCrudService extends StoreCrudServiceBase {
    @storeAsyncMethod
    public override async search(request: dyn.RestSearchRequest, primaryResourceId?: string) {
        return super.search(await withOrgId(request), primaryResourceId);
    }
}
```

Reads only. Writes take the org from the record being written — `create` carries an explicit
`org_id` field, and `update` / `delete` are addressed by an id the server already scopes.

### Wiring: register the schema, then use `withSchema`

A module registers its resources' REST paths once, in `init`:

```ts
// modules/identity/src/index.tsx
schemaRegistry.register([
    { schemaName: c.USER_SCHEMA_NAME,  resourcePath: 'v1/iam/users'  },
    { schemaName: c.ROLE_SCHEMA_NAME,  resourcePath: 'v1/iam/roles'  },
    // …
]);
```

`SchemaRegistry.get(name)` lazily fetches `/meta/schema`, caches it and derives a **zod validation
schema** from it, returning a `SchemaPack` = `{ schemaName, modelSchema, validationSchema,
restApi }`. It **throws if the registered name differs from the name the server returns** — see §3.

`withSchema(name, fn)` resolves the pack, runs `fn`, then compares the response's `schema_etag`
against the cached `modelSchema.etag` and **refreshes the registry when the backend model
changed**. Always go through it rather than holding a `SchemaPack` yourself:

```ts
export function searchUsers(request: t.SearchUserRequest): UserServiceResult<t.SearchUserResponse> {
    return withUserSchema(schema => schema.restApi.search(request));
}
```

### Business-specific calls alongside the standard ones

A service layer **is not limited to the standard endpoints**. It may add resource-specific calls,
in the same file, with the same never-throw contract — that is the point of having one service
module per resource. Examples from `coremart/modules/vendingMachine`:

```ts
// PUT …/kiosks/:id/kiosk-stocks/replace   — replace a whole shelf layout
// PATCH …/kiosks/:id/kiosk-stocks/bulk    — bulk sort_index / warning_quantity
// PATCH …/kiosks/:id/positions/upsert     — partial position updates
// POST …/kiosks/:id/kiosk-stocks/bulk     — bulk create
```

Also legitimate in the service layer: response shaping the UI must not do itself —
e.g. `searchUsers` masks `password` on every returned item; `createPayment` re-reads the record
because the create endpoint returns only `{ id, etag, createdAt }`.

### The transport underneath

`RestApi` delegates to `RequestMaker` (`@nikkierp/common/request`), a `ky` wrapper created once
by `MicroAppProvider` from `MicroAppProps.api`. It injects the `Authorization: Bearer` header from
`getAccessToken()`, handles token refresh/retry, sets JSON and multipart content types, and owns
the de-duplication map. Services should not construct their own `RequestMaker` — `RestApi`
defaults to `RequestMaker.default()`.

### Legacy pattern (being migrated)

`coremart/modules/vendingMachine` predates the dynamic-model registry: its services call
`request.get/post/put/patch/del` directly against a hardcoded `BASE_PATH` and convert case by
hand with `camelToSnakeObject` / `snakeToCamelObject`. **This is the pattern being migrated away
from**, resource by resource (payment is the furthest along). New code should register a schema
and use `RestApi`; when touching a legacy service, keep the three-layer split (service → commands
→ bus) even if the transport is still raw.

## 3. Dynamic-model schema names

A frontend `schemaName` must equal the backend Go constant **verbatim** — `SchemaRegistry` throws
if the registered name differs from what the server returns.

Form: `{module}_{entity}` in snake_case, **never dotted** — `iam_user`, `iam_group`, `iam_org`,
`iam_orgunit`, `iam_role`, `iam_entitlement`, `iam_role_user_assignment`, …

They are declared as `XSchemaName` in
`backend-coremart26-mono/nikkierp/modules/{module}/domain/models/{entity}.go`. **Read the constant
there rather than guessing from the resource path** — note that `iam_org` is *not* `iam_organization`
even though the REST path is `v1/iam/organizations`.

The schema name is also the middle segment of every command name for that resource
(`iam.iam_user.search_users`), so getting it wrong breaks both the API and the bus.
