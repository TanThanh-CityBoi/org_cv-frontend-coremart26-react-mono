# Dynamic schema UI

The view engine (doc 03) decides **which fields appear in which block**. This document covers the
other half: the backend model schema decides **what each field is** — its type, whether it is
required, whether it points at another record — and the form renders itself from that. No resource
gets hand-written form code.

Worked example throughout: the role create page, `/{org}/iam/roles/new`.

## 1. The render path

```
pages/role.ts            resourceDetailProps({ formSections: [{ header, fields }] })
  └─ definePage          route 'roles', split-view template
      └─ ResourceDetail  useDynamicModel(schemaName) → SchemaPack; id === 'new' ? create : update
          └─ ResourceCreate         buildCreateNodes: one RESOURCE_CREATE_COLUMN per block
              └─ ResourceCreateBlock        hides itself when no field survives (§7)
                  └─ ResourceCreateFieldGroup
                      └─ AutoField          switches on data_type.name (§4)
```

| Hop | File |
| --- | --- |
| Page metadata | `nikkierp/modules/identity/src/pages/role.ts` |
| Template → detail | `libs/viewkit-mantine/src/pages/resourceDetail/template.tsx` |
| Create / update split | `.../resourceDetail/ResourceDetail.tsx` |
| Blocks | `.../resourceDetail/resourceCreateParts.tsx`, `.../resourceUpdateParts.tsx` |
| Field dispatch | `libs/ui/src/components/form/fields.tsx` |

`ResourceDetail` renders `ResourceCreate` when the route id is the literal `new`, and
`ResourceUpdate` otherwise. `childrenNodes` reach only the update path — during create there is no
record id for a related-records table to filter by.

## 2. Fetching the schema

`useDynamicModel(schemaName)` publishes `core.dynamic_model.get_schema`, which the registry resolves
to `GET {resourcePath}/meta/schema` — for roles, `/v1/iam/roles/meta/schema`. The response is cached
per schema name and shared by every form on the page.

The registry throws when the returned `name` does not match the one requested. **A mismatch shows up
as a page stuck on its loading spinner**, not as an error message — the schema promise rejects and
nothing downstream ever resolves. The organizations page sat in that state until its constant was
corrected from `iam_organization` to the backend's actual `iam_org`; `iam_orgUnit` vs `iam_orgunit`
was the same bug one casing apart. When a resource page hangs with only a `meta/schema` request in
the network tab, compare the two names first.

## 3. The payload

Emitted by `ModelSchema.ToSimplized()`
(`backend .../nikkierp/common/dynamicmodel/model/model_schema.go`):

| Key | Meaning |
| --- | --- |
| `name` | Must equal the frontend `schemaName` verbatim |
| `etag` | Schema version; changes invalidate the cache |
| `fields` | `{ [fieldName]: ModelSchemaField }` |
| `label` | Localized model name |
| `exclusive_required_field_groups` | Groups where exactly one member may be set (§9) |
| `record_label_field` | The field that names a record to a human (§5) |
| `record_sub_label_field` | Optional secondary field under the main label |
| `to_relations` | Outgoing edges — this schema owns the foreign key |
| `from_relations` | Inverse edges — the peer owns the key |

A relation entry is `{ edge, src_field?, dest_schema_name, relation_type }`, where `relation_type`
is one of `one:one`, `one:many`, `many:one`, `many:many`. **`src_field` is absent on many-to-many
edges**, which have no column on this table — that absence is what keeps §5's lookup honest.

Field flags that drive rendering: `is_primary_key`, `is_system_field`, `is_auto_generated`,
`no_update`, `is_required_for_create`, `is_required_for_update`.

## 4. Field rendering

`AutoField` switches on `data_type.name`:

| `data_type.name` | Renders |
| --- | --- |
| `string`, `email` | `TextInput` |
| `secret` | `PasswordInput` |
| `int32` | `NumberInput` |
| `decimal` | `NumberInput`, value kept as a **string** — see below |
| `boolean` | `Checkbox` |
| `nikkiDate` | `DateInput` |
| `nikkiDateTime` | `DateTimePicker` |
| `nikkiTime` | `TimeInput` |
| `nikkiLangJson` | Per-locale inputs |
| `enumString` | `Select`, **only** when `options.enumValues` is present |
| `ulid` | Relation select, or a text input — see §5 |
| everything else | Nothing; the field is hidden and its block may disappear (§7) |

Two rules cut across the switch:

- A field with `no_update`, in update mode, renders as **text rather than an input** — the server
  would refuse the change, so offering the control invites a silent failure.
- A field with `is_auto_generated` gets **no input in either form mode**. `created_at`,
  `updated_at` and `is_archived` are all auto-generated on `iam_role`; without this rule they became
  editable pickers the moment `nikkiDateTime` gained a renderer.

A `decimal` is carried as a **string** for its whole life in the browser — never parsed into a
JavaScript number. The backend sends values a float64 cannot hold exactly (a UoM conversion factor
of `0.453592`, a bound of `1000000000000`), and business rules depend on them arriving back
unchanged. `DecimalInputField` therefore exists alongside `NumberInputField` rather than reusing
it: the latter filters on `typeof value === 'number'`, which would blank a string value out and
silently discard the edit. `data_type.options.scale` becomes the input's `decimalScale`.

> Adding a type means three edits: a case in `AutoField` (or in its
> `renderIdentityOrTemporalField` helper, which exists to keep the main switch under the
> function-length limit), an entry in `RENDERABLE_DATA_TYPES`
> (`libs/common/src/dynamicModel/model_schema.ts`), and a row above. `model_schema.test.ts` fails
> if the first two drift apart.

## 5. `ulid` → `to_relations` → searchable select

A `ulid` is either a foreign key or a bare identifier, and the schema settles which:

1. Look the field up as a `src_field` in `to_relations` (`findRelationBySrcField`).
2. **Hit** → the entry's `dest_schema_name` is the target resource. Render `RelationSelectField`.
3. **Miss** → render a plain text input.

On `iam_role` this yields, from the live payload:

```json
{"edge":"owner_group","src_field":"owner_group_id","dest_schema_name":"iam_group","relation_type":"many:one"}
{"edge":"owner_user", "src_field":"owner_user_id", "dest_schema_name":"iam_user", "relation_type":"many:one"}
```

so both owner fields become pickers, while **`org_id` — a `ulid` with no `EdgeTo` behind it — stays
a text input**. That is not an oversight: the backend declares no relation for it.

### Labelling a record

The target's own schema names its display field, so nothing is hardcoded per resource:

```
label     = targetSchema.record_label_field      // iam_user → display_name, iam_group → name
subLabel  = targetSchema.record_sub_label_field  // iam_user → email
```

Declared on the backend with `RecordLabelField(...)` / `RecordSubLabelField(...)`. When a schema
declares none, the select falls back to `id`.

A label field may be a plain string (`display_name`) **or** a `nikkiLangJson` object (`name`).
Render it through `useLocalize()` — or the `JsonLangText` component where a node is wanted — both of
which accept either shape. Never interpolate a LangJson into a template string; it yields
`[object Object]`.

> **Rollout note.** `record_label_field` is currently declared only on the IAM models. The builder
> validates that a declared field exists but does not yet require one, because ~60 schemas across 8
> modules predate the property. Making it mandatory is a follow-up.

## 6. Populating the select through the command bus

The select searches the target with `core.resource.{dest_schema_name}.search` and back-fills a
selected record with `…get_by_id`.

**This is why the generic command naming matters.** The command is *derived from the schema name*,
which is all the relation gives us. A hand-written name like `iam.iam_group.search_groups` cannot be
derived, so a relation select could never find it. The identity module's group, role and
organization resources were migrated to the generic path for exactly this reason; the exported
constants (`GroupCommands.SEARCH`, …) kept their names, so page metadata was untouched.

Mechanics:

- **Debounce** 300 ms (`useDebouncedValue`), so a request goes out per pause, not per keystroke.
- **Search graph** `{ if: [labelField, '*', term] }` — `*` is the contains operator. An empty term
  sends no filter.
- **Page size** 20; the last page is cached so an in-flight request never blanks the dropdown.
- **No client-side re-filtering.** Mantine's `Select` is given `filter={({options}) => options}`,
  because the server already decided what matches.
- **Back-fill.** In update mode the form opens with an id set, and that record need not be on the
  first page of results — Mantine drops a `value` absent from `data`, so the field would look empty.
  A one-shot `get_by_id`, guarded by a ref of already-resolved ids, supplies the missing option.
  Until it lands the raw id is shown, which is truthful and less jarring than a blank.

> **Cross-module limitation.** The Shell subscribes the `core.resource` prefix eagerly, so these
> commands never trigger a lazy module load. A relation pointing at a schema whose module has not
> loaded is served by the generic fallback and may fail to resolve; the select then renders disabled
> with the error rather than crashing the form. `resolveService` deliberately does **not** cache
> that fallback, so the owning module's service takes effect as soon as it registers. Making the
> prefix handler consult the module registry and trigger a load is a follow-up.

## 7. Hiding what has nothing to show

`isFieldVisible(modelSchema, field, mode, values?)` and `hasVisibleField(...)`
(`libs/viewkit-mantine/src/pages/resourceDetail/fieldVisibility.ts`) decide both which fields render
and whether a block is worth drawing at all.

| Rule | create | update | read |
| --- | --- | --- | --- |
| Not in `fields` | hidden | hidden | hidden |
| `is_primary_key` | hidden | hidden | shown if set |
| `is_auto_generated` | hidden | hidden | shown if set |
| `is_system_field` | hidden | type decides | shown if set |
| Type has no input | hidden | hidden | **shown** |
| Value empty | shown | shown | **hidden** |

Read mode differs on the last two rows because it goes through `renderDisplayFieldValue`, which can
print a value of any type — while a blank row communicates nothing, so an unset field is dropped.

A block renders only when at least one of its fields is visible; otherwise the header goes too. On
the role form this removes the audit block (`created_at`, `updated_at` — both auto-generated) from
create and update entirely.

## 8. Blank optional fields

`buildValidationSchema` turns each field into a zod schema. For an **optional** field it first
blanks the submitted value — `''`, `null`, `undefined`, or an empty array all become `undefined` —
and the parsed object then drops every `undefined` key.

Both halves are load-bearing:

- **Blanking** stops a spurious error. An untouched text input submits `''`, which is not a ULID, so
  validating it directly reported `err_invalid_data_type` on `org_id` — a field the user was free to
  leave alone.
- **Dropping the key** keeps the property out of the request body entirely, so the server sees an
  untouched field as absent rather than as an explicit empty value.

The blank test is deliberately narrower than the one behind required-field validation: `0` and
`false` are real values a number or checkbox field may hold, and must never be blanked away.
A malformed value is still rejected — only genuinely empty input is forgiven.

> Because of the key-dropping transform, `buildValidationSchema` returns a `ModelValidationSchema`
> (a schema that *parses to* an object), not a `ZodObject`. `zodResolver` needs nothing more; code
> wanting per-field detail should read `modelSchema.fields`.

## 9. Exclusive required field groups

`exclusive_required_field_groups: [["owner_group_id", "owner_user_id"]]` means exactly one of the
two must hold a value. Declared on the backend with
`ExclusiveRequiredFields(RoleFieldOwnerGroupId, RoleFieldOwnerUserId)`.

The form's part is small and deliberately so: when one member holds a value, the others render
**disabled with a hint**. Nothing is auto-cleared — the select is `clearable`, so switching owners is
one click, and a value the user entered is never discarded behind their back. A disabled field still
displays its value, because that value is still in form state and will still be submitted.

> **No client-side validation of the rule.** The server rejects zero or several members set, and the
> error lands on the field like any other. Duplicating the rule in the zod schema would create two
> definitions of correctness that can drift; one authority is better than two that disagree.

## 10. Naming conventions

| Where | Convention | Example |
| --- | --- | --- |
| Backend request/response payloads | `lower_snake_case` | `owner_user_id`, `record_label_field` |
| Frontend variables, properties, functions | `camelCase` | `ownerUserId`, `findRelationBySrcField` |
| Frontend constants | `UPPER_SNAKE_CASE` | `SEARCH_DEBOUNCE_MS`, `PAGE_SIZE` |

**A frontend type modeled after a backend type uses `camelCase` members, and the payload is
translated field by field at an explicit boundary — never by an automatic case-transforming
algorithm.**

```ts
// Do this — explicit, greppable, and it fails to compile when a field is added or renamed.
function toRole(payload: RolePayload): Role {
	return {
		id: payload.id,
		ownerUserId: payload.owner_user_id,
		ownerGroupId: payload.owner_group_id,
	};
}

// Not this.
const role = camelizeKeys(payload) as Role;
```

An automatic transform mangles `org_id` / `orgId` / `orgID` inconsistently, cannot express a field
whose frontend name legitimately differs from its wire name, and turns a compile-time contract into
a runtime one that fails far from its cause.

> **Current exception: `ModelSchema` and friends.** The dynamic-model types in
> `libs/common/src/dynamicModel/model_schema.ts` mirror the backend JSON tags verbatim
> (`to_relations`, `is_required_for_create`, `record_label_field`). They predate this rule, there is
> no translation layer anywhere in the codebase, and they are read reflectively —
> `fieldDef['is_required_for_' + formVariant]` in `useFieldData` — which a rename would break.
> **The rule above governs new types; `ModelSchema` is not exempt on merit, only on sequencing.**
> Renaming it is its own change with its own test pass.
