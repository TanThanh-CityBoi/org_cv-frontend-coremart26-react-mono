# View Engine

## 1. Purpose: declarative UI, framework-agnostic

Pages in this codebase are **authored as plain JSON metadata, not JSX**. A module says *what* a
page is; a **view kit** decides *how* it is drawn.

```ts
// modules/identity/src/pages/user.ts — the entire "users" page
definePage({
    routePath: 'users',
    template: splitView.template,   // 'nikkierp.mantine.pages.templates.resourceSplitView.v1'
    props: splitView.props,         // plain JSON, JSON.stringify-able
})
```

Three properties follow from that, and they are the whole reason the engine exists:

**Declarative.** A page is data. Adding a resource CRUD screen means writing a props object, not
a component tree — so the same page can be produced by a code generator, stored in a database, or
one day drawn in a visual page builder (`engine.describe()` already exposes the manifest for it).

**Serializable across a bundle boundary.** Every metadata field must survive
`JSON.parse(JSON.stringify(node))`. **No classes, no functions, no `instanceof`, no live
objects.** This is what lets an out-of-repo micro-app ship page definitions the host can render
with *its* renderers. Where JS would normally reach for a function, metadata uses a serializable
substitute:

| JS instinct | Metadata form |
| --- | --- |
| `row => row.status !== 'active'` | `ConditionExpression`: `{ field: 'status', operator: 'not_equal', value: 'active' }` |
| `value => <Badge…>` | `FieldRendererSpec`: `{ renderer: 'badge', colorMap: {…} }`, resolved at render time |
| `<SplitView left={<UserList/>}>` | `TemplateRef`: `{ template: '…resourceList.v1', props: {…} }` |

**UI-framework agnostic.** `nikkierp/libs/viewengine` contains **no Mantine, no UI library, no
module** — enforced by lint, not convention. Its only tie to React is one type alias:

```ts
// core/renderResult.ts
export type RenderResult = React.ReactNode;
```

> The single React seam of the view engine. Swapping the rendering engine (React → Vue, etc.)
> means changing this alias and the concrete templates / component renderers, never the metadata
> JSON, the registries, `MetaPage`, or `MetaComponent`.

Diagnostics inside the core are rendered with plain DOM and inline styles for the same reason —
the core cannot import a `<Text>` or an `<Alert>`.

## 3. How it works

### 3.1 Registry

`ViewEngine` (`engine/ViewEngine.ts`) is four `Map`s — page templates, component renderers, field
renderer factories, installed kits — behind two deliberately narrow faces:

- `IViewRegistry` — **write-only**, handed to `IViewKit.contribute`.
- `IViewResolver` — **read-only**, handed to renderers and templates.

It is **an instance, never a module singleton**: a separately built micro-app bundle gets its own
copy of the module, so a singleton `Map` there would be invisible to the host. The Shell creates
one in `MicroAppHostProvider`, installs the Mantine kit, and passes it to every micro-app as
`host.viewEngine` (see [Micro Frontend architecture](<./01. Micro Frontend architecture.md>)).

### 3.2 Contribution ids

`{vendor}.{kit}.{kind}.{name}.v{major}` — e.g. `nikkierp.mantine.pages.templates.resourceList.v1`,
`nikkierp.identity.components.rolePicker.v1`, `acme.crm.components.dealPipeline.v1`.

| Segment | Rule |
| --- | --- |
| `{vendor}` | The owning organisation. `nikkierp` is reserved (see the vendor policy below). |
| `{kit}` | The kit's own id suffix — `mantine`, `identity`. It names the folder the renderer lives in, so an id read in a page definition points at its source. |
| `{kind}` | `pages.templates` or `components`. |
| `{name}` | lowerCamelCase. A component that is a **part of** a composite carries a dotted parent path: `resourceForm.column`, `resourceCreate.header`. |
| `v{major}` | Part of the id, not metadata about it. |

- Compared **verbatim**. No normalization, no aliasing. The engine parses only segment 0
  (`{vendor}`) to apply the conflict policy; the rest is opaque.
- **The major version is part of the id.** A breaking props change ships as a new `.v2` id
  registered *alongside* `.v1` — never as a mutation of the existing schema.
- Duplicate registration **throws** `ViewEngineConflictError` unless `{ override: true }` is
  passed. Silent last-write-wins is the worst failure mode in a plugin system; because
  registration happens during `init()`, the Shell surfaces the throw in its error panel rather
  than the UI quietly rendering the wrong template.
- **Vendor policy:** `nikkierp` is reserved. A third-party kit may **override** a `nikkierp.*`
  contribution (deliberate re-skinning) but may never **create** one — otherwise it could squat an
  id a future built-in wants. Violation → `ReservedVendorError`.

Why the full form for components too: the registry is one flat namespace shared by every kit
loaded into the host. Under bare names (`resource_table`, `resource_form` — what this kit used
until the convention was applied) two independently written kits collide on the obvious word for
the obvious widget, and `vendorOf()` returns the whole string, so the reserved-vendor check
protects nothing. Under the full form a collision needs the same vendor *and* the same kit *and*
the same name — which means one team owning both, where a collision is a mistake they can fix
rather than an accident between strangers. The dotted parent path is what keeps that readable:
sorted alphabetically, the parts of one composite sit together, and `resourceForm.column` says
where the component belongs without anyone having to open the file.

> **The one exception: field-renderer names stay bare** — `avatar`, `badge`, `translated`.
> They are not contribution ids: `registerFieldRenderer(name, factory)` keys its own namespace,
> and the names appear inline in page JSON as `{ renderer: 'badge' }`, where a five-segment id
> would drown the spec it labels. Use the exported constants from `@nikkierp/viewkit-mantine/ids`
> rather than hardcoding either kind.

### 3.3 Metadata node types

```ts
type PageNode = {
    type: 'page',
    routePath: string,
    template?: ContributionId,   // omit for a fully custom page
    props?: unknown,
    children?: ComponentNode[],
};

type ComponentNode = {
    type: 'component',
    component: ContributionId,
    props?: Record<string, unknown>,
    children?: ComponentNode[],
};

type TemplateRef<TProps> = { template: ContributionId, props?: TProps };
```

Nesting has **two distinct forms**, and they are not interchangeable:

- `children` / `childrenNodes` → an inline **component** subtree, rendered by `MetaComponent`.
- A `TemplateRef` **inside props** → a nested **template** invocation, rendered by
  `renderTemplateRef`. This is how the split view hosts a list template in one pane and a detail
  template in the other — including a third party's template — instead of hard-coding one concrete
  props type.

### 3.4 The render pipeline

```
PageNode
  │ compilePage(node, engine) → { routePath, element: <MetaPage node/> }
  │     routePath = template.routePattern?.(node) ?? node.routePath
  ▼
<MetaPage>                          ── provides PageContext
  ├─ template? → engine.getPageTemplate(id)
  │                ↓ missing → <UnknownTemplate/>
  │              validateProps(template.propsSchema, node.props)
  │                ↓ issues  → <InvalidProps/>
  │              template.createProps?(value, children)      // pure adaptation, plain data only
  │              template.render(params, { routePath, childrenNodes, engine })
  │                    └─ may call renderTemplateRef(props.primary, runtime) ─┐
  └─ no template → <MetaComponent node={children}/>                          │
                                                                             │
<MetaComponent>  ← per node: page-context check, depth cap, ────────────────┘
                   engine.getComponentRenderer(type),
                   validateProps(renderer.propsSchema), renderer.render(props, { children, engine })
```

Key behaviours:

- **Props are validated before any renderer runs**, so a template/renderer receives typed data and
  never reaches into the raw node or does an `instanceof` check.
- **Invalid props render a diagnostic panel; they do not throw.** One bad page does not take down
  the app. Every kit props schema is `.strict()`, so a misspelled key is a *visible* error rather
  than a silent no-op.
- Validators must be **synchronous** Standard Schema v1 (zod 4 satisfies it natively; valibot and
  arktype work too). An async validator throws — it is a programming error, not a runtime state.
- **The route shape belongs to the template**, via `routePattern(node)`. `compilePage` knows no
  template id. Split view contributes `` `${node.routePath}/:id?` `` itself; a wizard could
  contribute `/:step?` and a calendar `/:year/:month?` the same way.
- `MetaComponent` refuses to render outside a page (`PageContext`) and caps recursion at
  `MAX_COMPONENT_DEPTH`.

### 3.5 Field renderers: resolved at render time

Field renderers are registered as **factories over a serializable spec**, and resolved during
render by `useFieldRenderers` / `engine.resolveFieldRenderers(specs)` — never baked into the page
at build time.

```ts
// authoring (plain JSON, in the page definition)
fieldRenderers: {
    avatar_url: { renderer: 'avatar' },
    status: { renderer: 'badge', prefix: 'status.', colorMap: { active: 'green', locked: 'orange' } },
}

// registration (in the kit)
registry.registerFieldRenderer(FIELD_RENDERER_BADGE, (spec) => {
    const { colorMap, prefix } = badgeSpecSchema.parse(spec);
    return new BadgeFieldRenderer({ colorMap, translationKey: prefix ? v => `${prefix}${v}` : undefined });
});
```

Closures are fine *inside* a factory; they were only a problem when the closure **was** the
serialized artifact. Resolving late buys three things at once: the page stays serializable, the
lookup hits the host's engine rather than a module singleton, and a **later-loading kit can still
contribute a renderer** an already-authored page asks for.

### 3.6 Where the data comes from

The engine renders; it does not fetch. A kit's page components get their data by publishing
**commands** on the Shell-hosted bus. Page props name commands as strings
(`searchCommand: UserCommands.SEARCH`, `standardActionCommands.getById`, …), and hooks like
`useResourceSearch` resolve the dynamic-model `SchemaPack` and publish the search command. So a
page definition stays plain JSON while still being wired to a real backend — see
[Service and API](<./02. Service and API.md>).

## 4. Developing and registering new UI elements

All three kinds share the same shape: **an id, a props schema, a `render`** — then one line in the
kit's `contribute`.

### 4.1 A new component renderer

```
libs/viewkit-mantine/src/components/myWidget/
    props.ts            // zod schema, .strict(), with .default()s
    MyWidget.tsx        // the IComponentRenderer + the React component
```

```ts
// props.ts
export const myWidgetPropsSchema = z.object({
    header: z.string().min(1),          // i18n KEY, not a label
    translationNs: z.string().min(1),
    expanded: z.boolean().default(true),
}).strict();
export type MyWidgetProps = z.infer<typeof myWidgetPropsSchema>;
export type MyWidgetPropsInput = z.input<typeof myWidgetPropsSchema>;   // pre-defaults, for builders
```

```tsx
// MyWidget.tsx
export const myWidgetRenderer: IComponentRenderer<MyWidgetProps> = {
    type: MY_WIDGET,                                  // id constant from ../../ids
    propsSchema: myWidgetPropsSchema,
    render(props, runtime) {                          // (props, runtime) — never (node)
        return <MyWidget props={props} runtime={runtime} />;
    },
};
```

Render nested children with `<MetaComponent node={runtime.children} />`. Note `render` returns a
`RenderResult`, so hooks belong in the inner React component, not in `render` itself.

### 4.2 A new page template

```tsx
export const myPageTemplate: IPageTemplate<MyPageProps> = {
    id: MY_PAGE_TEMPLATE,
    propsSchema: myPagePropsSchema,
    routePattern: node => `${node.routePath}/:id?`,        // optional — own your route shape
    createProps: (params, childrenNodes) => ({ ...params }), // optional, pure, plain data only
    render: (params, runtime) => <MyPage params={params} routePath={runtime.routePath} />,
};
```

`runtime` is `{ routePath, childrenNodes, engine }`. To host another template inside yours, put a
`TemplateRef` in your props and call `renderTemplateRef(params.someRef, runtime)`.

### 4.3 A new field renderer

Implement `IFieldRenderer` (`render(rawValue, translatedValue)`, optional `translationKey(value)`),
define a `.strict()` zod schema for its spec, and register the **factory**:

```ts
registry.registerFieldRenderer(FIELD_RENDERER_MY_THING, spec => new MyThingRenderer(mySpecSchema.parse(spec)));
```

### 4.4 Wire it up (4 steps, in order)

1. **Add the id** to `libs/viewkit-mantine/src/ids.ts` — full `{vendor}.{kit}.{kind}.{name}.v{major}`
   (§3.2), for a component just as much as for a template. A module's own kit puts its ids in
   `modules/{module}/src/viewkit/ids.ts` under its own `{kit}` segment.
2. **Register it** in `kit.ts` → `mantineViewKit.contribute(registry)`. One reviewable list; never
   an import side effect.
3. **Export a typed builder** from `props.ts` so authors don't hand-write JSON. Builders
   `.parse()` **eagerly**, so a bad page fails where it is authored rather than at render time:
   ```ts
   export function myPageProps(input: MyPagePropsInput): TemplateRef<MyPageProps> {
       return { template: MY_PAGE_TEMPLATE, props: myPagePropsSchema.parse(input) };
   }
   // component nodes return a ComponentNode instead:
   export function myWidgetNode(input: MyWidgetPropsInput): ComponentNode {
       return defineComponent({ component: MY_WIDGET, props: myWidgetPropsSchema.parse(input) as Record<string, unknown> });
   }
   ```
4. **Use it in a module's `pages/*.ts`**, importing only from `@nikkierp/viewkit-mantine/props`.

### 4.5 A whole new kit (out of repo)

```ts
export const acmeKit: IViewKit = {
    id: 'acme.crm',                                  // your own vendor
    version: '1.0.0',
    engineApiVersions: [VIEW_ENGINE_API_VERSION],    // engine throws on mismatch
    contribute(registry, ctx) { /* registerPageTemplate / registerComponentRenderer / … */ },
};
export function contributeAcmeKit(engine: IViewEngine): void { engine.use(acmeKit); }
```

`engine.use(kit)` is **idempotent per `kit.id`** — a second call is a no-op. Register `acme.*` ids
freely; you may `{ override: true }` a `nikkierp.*` id to re-skin it, but you may not create one.

### 4.6 Authoring a page in a module

```ts
// modules/{module}/src/pages/{entity}.ts   — plain data, no JSX
export function buildUserPages(): PageNode[] {
    const splitView = resourceSplitViewProps({
        primary:   resourceListProps({ schemaName: c.USER_SCHEMA_NAME, searchCommand: UserCommands.SEARCH, … }),
        secondary: resourceDetailProps({ schemaName: c.USER_SCHEMA_NAME, … }),
    });
    return [definePage({ routePath: 'users', template: splitView.template, props: splitView.props })];
}
```

Then hand the pages to `ViewEngineRouter`, which calls `compilePage` for each and mounts them as
routes:

```tsx
<ViewEngineRouter microAppProps={props} engineProps={{ pages, indexElement: <h1>Identity</h1> }} />
```

`indexElement` is supplied by the owning module — it used to be a hardcoded `<h1>Identity</h1>`
inside the shared library, so every module that adopted the router rendered IAM's landing page.

#### Appending sections to a resource detail page

Pass `childrenNodes` (`ComponentNode[]`) to `resourceDetailProps()`. They render **after** the
form as its siblings, and **only in update mode** — `ResourceDetail` gives them to `ResourceUpdate`
and not to `ResourceCreate`, which is correct: during create there is no record id to filter
related records by.

Wrap each section in **`collapsible_section`** (`collapsibleSectionNode`), giving it a `header` and
its `translationNs` so it renders as a titled, collapsible block. It touches no form context, so it
is safe here. Do **not** reach for `resource_form__section`: that is the resource form's own
section, it always renders a `SectionActionBar` bound to the enclosing form, and `ResourceUpdate`
is its only legitimate emitter.

Embed a related-records table with `resource_table` (`resourceTableNode`). Its `filterGraph` is a
plain-JSON search graph in which any whole `${param}` string is replaced by the current route
param, and `linkRoutePath` points rows at a *different* page than the current one:

```ts
collapsibleSectionNode({ header: 'role_sections_assignedUsers', translationNs: c.IAM_MODULE }, [
    resourceTableNode({
        schemaName: c.USER_SCHEMA_NAME, translationNs: c.IAM_MODULE,
        searchCommand: UserCommands.SEARCH,
        filterGraph: { if: ['roles', 'linked', '${id}'] },   // `linked` filters across a many edge
        linkField: 'id', linkRoutePath: 'users',
    }),
])
```

See `nikkierp/modules/identity/src/pages/role.ts`.

## 6. Authoring a stateful page as metadata

A resource page is pure configuration: `resourceDetailProps({ … })` describes it and the template
does the rest. A page with its own behaviour — a wizard, a stage machine, anything with state that
is not a record — looks like it has to be hand-written JSX. It does not, and it should not be.
`RoleAssignmentPage` is the worked example; `ResourceUpdate` is the same shape one layer down.

### 6.1 The rule

> **A page — and a page template — never imports a custom visual component directly.**
> UI-library components (Mantine, `@tabler/icons`) are fine. Anything authored in this repo is
> rendered from metadata.

The React a template may import is limited to **infrastructure**: its own providers,
`PageContainer`, and `MetaComponent`. Everything a user can see goes through the registry.

Why: an id is the only handle anyone else has. A component composed as JSX cannot be placed by a
page definition, cannot be reordered without editing React, cannot be overridden by a kit that
loads later, and does not show up in `engine.describe()`. "Nothing addresses it from page JSON
yet" is not a reason to skip the id — it is a description of the problem the id solves.

### 6.2 The shape

```
Template.render(params)
  └─ XProvider              — owns the state; publishes it as context
       └─ PageContainer     — the page shell (absolute inset, scroll, paper bg)
            └─ MetaComponent node={buildXNodes(context)}
```

`buildXNodes` is a **plain function of the context** returning `ComponentNode[]`, memoised on the
context. See `ResourceUpdate.tsx` (`buildUpdateNodes`) and
`nikkierp/modules/identity/src/viewkit/pages/RoleAssignmentPage.tsx`
(`buildRoleAssignmentNodes`).

```tsx
export function RoleAssignmentPage({ props }: { props: RoleAssignmentProps }): React.ReactNode {
    return (
        <RoleAssignmentProvider params={props}>
            <PageContainer>
                <RoleAssignmentContent />
            </PageContainer>
        </RoleAssignmentProvider>
    );
}

function RoleAssignmentContent(): React.ReactNode {
    const context = useRoleAssignmentContext();
    const nodes = React.useMemo(() => buildRoleAssignmentNodes(context), [context]);
    return <MetaComponent node={nodes} />;
}
```

### 6.3 Context carries data; JSON carries placement

The wizard's six components declare `propsSchema: z.object({}).strict()` — **no props at all** —
and read everything from `useRoleAssignmentContext()`.

That is not laziness, it is the only thing that can work: metadata must survive
`JSON.stringify` (§1), and `onClick`, `disabled` and a `Map<string, Role>` do not. So the split is
fixed — **page JSON says what appears and where; the provider says what it does and with what.**
A context-bound component belongs to exactly one page family and says so by throwing from its
`use…Context()` hook when rendered anywhere else.

Props are still the right answer for anything genuinely configurable — `collapsible_section` takes
its `header` and `translationNs` as props precisely because those vary per placement.

### 6.4 Conditional subtrees are plain JS

```ts
return [
    pageHeaderNode({ titleLvl1: { textKey: context.params.titleKey } },
        [defineComponent({ component: ROLE_ASSIGNMENT_ACTIONS })]),
    ...(context.error != null ? [defineComponent({ component: ROLE_ASSIGNMENT_ERROR })] : []),
    ...(context.stage === 'select' ? buildSelectNodes() : buildConfirmNodes()),
];
```

There is no `if` component and there should not be one. The condition already lives in the context
the memo depends on; moving it behind a contribution id would only hide it from the one place a
reader looks — the builder.

### 6.5 Picking the pieces

**`page_header`** titles a page from either source, chosen per title line:

| Spec | Resolves to |
| --- | --- |
| `{ schemaField: 'display_name' }` | that field of the `record` in `PageHeaderContext`, formatted through the model schema (so a `nikkiLangJson` renders as text, not `[object Object]`) |
| `{ textKey: 'assignment.rolesOf' }` | `t(key, titleParams)` in the context's namespace |

The page supplies whichever half it has by wrapping its subtree in `PageHeaderProvider`
(`{ translationNs, record?, modelSchema?, titleParams? }`). A resource page fills in the record;
a wizard fills in `titleParams` and nothing else. **Child nodes of the header become its action
row** — that is how a page contributes its own buttons without the header knowing what they do.
`resource_detail__header` is just this component plus the resource-specific adapter and the
Create/Close buttons.

**`collapsible_section` vs `resource_form__section`:**

| | Header | Action bar | Use when |
| --- | --- | --- | --- |
| `collapsible_section` | titled and collapsible with a `header`; none without one | none | anywhere — a related-records table, an appended detail section, a standalone block |
| `resource_form__section` | none | the enclosing form's `SectionActionBar` | never by hand; `ResourceUpdate` emits it as the form's own section |

The split is what keeps a Save button honest. `resource_form__section` reads the resource-update
context unconditionally and would throw outside a form, while nesting a second one inside a form
would give the page two Save buttons submitting the same record. `collapsible_section` reads no
form context at all, so it composes freely.

## 7. Rules and enforced boundaries

`eslint.config.mjs` encodes these as lint zones — a violation **fails the build**. Do not work
around them.

| Rule | Why |
| --- | --- |
| `libs/viewengine` may not import any kit, `@nikkierp/ui`, `@nikkierp/shell` or any module. | The core is implementation-free; that is the whole framework-agnostic claim. |
| `libs/ui` may not import a view kit. | Kits depend on `ui`, never the reverse. |
| Nobody outside the engine may import `@nikkierp/viewengine/engine` or `defaultViewEngine`. | That barrel exposes the singleton. Import `./core`, `./metadata` or `./render`; get the engine from `init` options or `useViewEngine()`. |
| `@nikkierp/ui/viewEngine` is deprecated. | Type shim awaiting deletion. |

`defaultViewEngine` exists **only** for standalone dev servers, Storybook and unit tests. In a
separately built bundle it registers into a `Map` the host cannot see — which fails *silently* at
runtime, the worst possible mode. Production code always gets the engine from
`host.viewEngine` (at `init`) or `useViewEngine()` (at render). For tests use
`createTestEngine()` from `@nikkierp/viewengine/testing`, which hands back a fresh instance each
call.

Two more conventions worth internalising:

- **Metadata must stay JSON.** If you find yourself wanting a function in props, you want a
  `ConditionExpression`, a `FieldRendererSpec`, or a command name string instead.
- **i18n keys, not labels.** Page metadata carries `labelKey` / `header` / `translationNs`; the
  renderer translates at render time, because a page definition is built before any namespace is
  guaranteed loaded.
