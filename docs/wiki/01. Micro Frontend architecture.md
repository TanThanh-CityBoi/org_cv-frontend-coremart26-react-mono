# Micro Frontend Architecture

## 1. Shell and Micro Apps

The frontend is a **single-page app assembled at runtime from independently built bundles**.

| Role | What it is |
| --- | --- |
| **Hosting app** (`apps/webapp`) | The Vite entry point. Its `src/main.tsx` declares a `MicroAppMetadata[]` — the list of micro-apps this build ships — and renders `<MicroAppShell microApps={…} />` inside a `<Router>`. |
| **Shell** (`nikkierp/modules/shell`) | The MFE Shell *implementation*: chrome (menu bar, layouts, routes, error boundary), authentication, and the mounting points for micro-apps. |
| **Shell support lib** (`nikkierp/libs/shell`) | The reusable machinery a Shell needs: `MicroAppManager`, `MicroAppHostProvider`, the Shell command bus, auth service, env config, menu registry wiring. |
| **Micro App** (`{nikkierp,coremart}/modules/{name}`) | A feature module packaged as an MFE. Lazily downloaded, mounted as a **custom element** (web component), owns its own pages, services and command handlers. |

### Lifecycle of a micro-app

```
main.tsx declares MicroAppMetadata
  → MicroAppHostProvider creates host services once
  → <LazyMicroApp slug="iam"/> renders
  → MicroAppManager.fetchMicroApp(slug)   // dynamic import() or URL fetch, with retry + dependsOn
  → MicroAppManager.initPack(slug, pack)  // calls bundle.init(...) EXACTLY ONCE (result cached)
  → React.createElement(htmlTag)          // <microapp-iam> custom element mounts
  → <MicroAppProvider {...props}> renders the module's pages
```

`MicroAppMetadata` (`nikkierp/libs/ui/src/microApp/types.tsx`):

- `slug` — unique id **and** URL segment; **must match the backend ERP module name** (`iam`, `vending_machine`, …).
- `basePath` — URL base path; omit it and the app is widget-only.
- `htmlTag` — the custom-element tag name (`microapp-iam`).
- `bundleUrl` — a URL string *or* a function returning `import()`.
- `configUrl` — optional; the Shell fetches it and passes the result as `config`.
- `dependsOn` — slugs fetched before this one.

### The bundle contract

A micro-app's entry point **default-exports a `MicroAppBundle`** — an object with a single
`init(opts)` function that defines the custom element and registers everything the Shell and the
bus may need before the module is displayed.

`init` runs **once per slug**, outside React, and possibly *before the module is ever
displayed* (the bus loads a module lazily just to reach a handler). So it must be synchronous
for anything the bus or menu bar depends on, and must not assume a DOM or an i18n namespace.

`domType` decides the mount mode:
- `shared` — Light DOM; the micro-app shares the Shell's document (styles, Mantine theme).
- `isolated` — Shadow DOM; the bundle is fully encapsulated and re-initializes its own
  `RequestMaker`.

The step-by-step contract, with the reference implementation
(`nikkierp/modules/identity/src/index.tsx`), is doc
[05. ERP frontend module](<05. ERP frontend module.md>) §2.

## 3. Communication

### 3.1 The golden rule

**Modules never import each other.** `eslint.config.mjs` enforces this as a build-breaking lint
zone: a module may not import `@nikkierp/microapp-*` or `@coremart/microapp-*`. All cross-module
traffic goes through the **command bus**.

```
        ┌──────────────── Shell ────────────────┐
        │  MicroAppManager · CommandBus         │
        │  ViewEngine · MenuRegistry            │   ← created ONCE, instances
        └───┬───────────────┬───────────────┬───┘
      init()│         init()│         init()│
        ┌───▼───┐       ┌───▼───┐       ┌───▼───┐
        │  iam  │       │ drive │       │  vm   │
        └───────┘       └───────┘       └───────┘
             └──────── command bus ─────────┘        (never a direct import)
```

### 3.2 State isolation

**The Shell and the micro-apps do not share state, nor the thing that manages it.** No micro-app
reads another's state, and none reads the Shell's. The only ways data crosses that line are the
**command bus** (request/response, one handler per name) and the **event bus** (fire-and-forget
fan-out). Reaching into another module's store is not a shortcut, it is a coupling the bundle
boundary cannot survive: a separately-built micro-app gets its own copy of every module it imports,
so a store reached by import is not the store the other side is writing to.

Each side is then free to manage its own state however it likes. The supported way is a store of its
own, from `@nikkierp/ui/appState/store`.

`createModuleStore(name)` registers the store under the micro-app's slug — or `shell` for the Shell
— in `ModuleStoreRegistry`, and `MicroAppProvider` mounts it on a **dedicated react-redux context**.
That context is what enforces the isolation: the default context still belongs to the Shell, so
neither the Shell nor a sibling can select a micro-app's state even by accident.

Import from `@nikkierp/ui/appState/store`, not the `@nikkierp/ui/appState` barrel: the barrel also
re-exports `routingSlice`, which reads `window.location` at import time and so cannot be loaded
outside a browser.

`StoreCrudServiceBase` lives in `@nikkierp/ui/appState/store` rather than beside `CrudServiceBase`
in `@nikkierp/common`, because that package is framework-free — no React, no Redux, and a server
build with no decorator transform — and `dynamicModel/resourceCommands` instantiates the plain base
as its runtime fallback service.

`clientErrors` and `error` are separate because they render differently: a client error is a
validation or business rejection that belongs on the offending form field, while `error` is a
technical failure that belongs in a toast. A call returning client errors still **completed**, so its
status is `fulfilled` — which is why `useServiceLayer` exposes `isSuccess` (fulfilled *and* clean)
alongside `isFulfilled`, and why `isSuccess` is the one to test.

A module that has not created a store is unaffected and renders exactly as before.

The `@storeService` / `@storeAsyncMethod` / `@storeSyncMethod` reference — what each decorator
generates, why the installed methods do not dispatch, and the worked example — is doc
[05. ERP frontend module](<05. ERP frontend module.md>) §5.

### 3.3 Shell → Micro App: what gets passed

Two hand-offs, at two different times.

**(a) At `init` time** — `MicroAppBundleInitOptions`, from `MicroAppManager.initPack`:

| Field | Meaning |
| --- | --- |
| `htmlTag` | The custom-element tag the Shell chose (avoids collisions). |
| `slug` | The registered slug; also the `/{orgSlug}/{slug}` URL segment and the **menu registry key**. |
| `config` | JSON fetched from `configUrl`, if any (may carry `apiBaseUrl`). |
| `registerReducer` | Registers the module's reducer into the Shell's Redux store, namespaced by slug. |
| `commandBus` | Same object as `host.commandBus`; kept for backward compatibility. |
| `host` | `HostServices` = `{ commandBus, viewEngine, menuRegistry }`. |

**(b) At mount time** — `MicroAppProps`, set on the custom element by the Shell:

| Field | Meaning |
| --- | --- |
| `api` | `{ defaultBaseUrl, getAccessToken }` — used by `MicroAppProvider` to init `RequestMaker`. |
| `config`, `slug`, `domType` | As above. |
| `routing` | `{ basePath, location, navigator }` — lets the micro-app share the Shell's React Router history instead of owning one. |
| `commandBus`, `viewEngine` | The host instances, re-provided through React context. |
| `widgetName`, `widgetProps` | Set when mounted in widget mode instead of as a route. |

### 3.4 Host-owned services

`MicroAppHostProvider` (`nikkierp/libs/shell/src/microApp/MicroAppHostProvider.tsx`) constructs
the `MicroAppManager`, view engine (with the Mantine kit contributed), menu registry and command
bus **exactly once**, then `manager.setHostServices(host)`.

This is not a style choice. A separately built micro-app bundle gets **its own copy** of any
module it imports, so a module-level singleton registry inside the bundle is invisible to the
Shell. A module must therefore use the passed-in instances and never construct its own, and never
import `defaultViewEngine` (that singleton exists only for tests, Storybook and standalone dev
servers, and is fenced off by eslint zones).

At render time the instances are read from context: `useViewEngine()` /
`useCommandBus()` inside a micro-app, `useShellViewEngine()` / `useShellCommandBus()` /
`useShellMenuRegistry()` on the Shell side.

#### Reaching the bus outside React: `CommandBus.instance`

Context and `init` cover component code, but neither reaches a **service class**, which is
constructed at import time — before any provider mounts and outside `init`'s scope. For that,
`CommandBus` carries the same static pair `EventBus` has:

```ts
CommandBus.instance;               // ICommandBus | undefined
CommandBus.setInstance(bus);       // installs, but only when none is set
```

The Shell installs it in `MicroAppHostProvider` right after `createShellCommandBus(...)`, and
`MicroAppProvider` installs it beside `EventBus.setInstance(props.eventBus)`. The set-only-if-unset
guard is what makes both calls safe:

- **Light DOM (`SHARED`)** — the micro-app shares the Shell's module instance, so `instance` is
  already the Shell's bus and `MicroAppProvider`'s call is a no-op.
- **Shadow DOM (`ISOLATED`)** — the separately built bundle has its own copy of the module, so the
  assignment succeeds and installs the host's bus into that copy.

**Prefer `HostServices` / `useCommandBus()` wherever you can.** The singleton is a fallback for
code that has no other handle, not a general shortcut — reaching for it inside a component hides a
dependency the context would have made explicit. Guard for `undefined` and fail loudly, the way
`RequestMaker.default()` does; an unset bus means the host provider has not mounted yet, which is a
wiring bug rather than a state to tolerate.

### 3.5 Micro App ↔ Micro App: the command bus

`nikkierp/libs/common/src/commandBus` — a framework-agnostic, request/response broker.

**Contracts** (`types.ts`):

```ts
type Command<TPayload>  = { name: string, payload?: TPayload };
type CommandResponse<TData, TError> =
    | { data: TData, error: null }
    | { data: null, error: TError };          // exactly one side is non-null
type CommandHandler = (cmd: Command) => CommandResponse | Promise<CommandResponse>;
```

Build responses with the `ok(data)` / `fail(error)` helpers. **Handlers should not throw** — but
`publish` wraps a throw into `fail(error)` anyway, so a caller never has to `try/catch`.

**Naming.** `{module}.{schema}.{action}`, e.g. `iam.iam_user.search_users`,
`vending_machine.payment.create_payment`, `shell.layout.register_menu`,
`core.dynamic_model.get_schema`. The **first segment is the module slug** — the bus uses it for
lazy loading. Names are exported as a frozen constant object per feature (`UserCommands`,
`PaymentCommands`) so callers never hardcode strings.

**Registration.** One handler per name; a duplicate `subscribe` **overrides** the previous one and
logs a warning. `subscribe` returns an unsubscribe function; a feature's `registerXCommands(bus)`
collects them and returns a single teardown closure.

```ts
export function registerUserCommands(bus: ICommandBus): () => void {
    const unsubscribers = [
        bus.subscribe(UserCommands.CREATE, cmd => svc.createUser(payload(cmd))),
        bus.subscribe(UserCommands.SEARCH, cmd => svc.searchUsers(payload(cmd))),
        // …
    ];
    return () => unsubscribers.forEach(u => u());
}
```

Registration happens **synchronously inside `init`**, never in a `useEffect` — the bus must be
able to find a handler the moment a module finishes loading.

**Publishing.**

```ts
const response = await commandBus.publish<SearchUserResponse>({
    name: UserCommands.SEARCH,
    payload: { page: 0, size: 20 },
});
if (response.error) { /* handle */ }
```

In React, prefer the `useCommand(commandName)` hook (`@nikkierp/ui/hookhoc`), which returns
`{ publish, data, error, isPending }` and guards against out-of-order responses and unmounted
components.

**Lazy module loading.** If no handler matches, the bus splits the command name on `.`, takes the
first segment as the module name and asks its `ModuleLoader` to load it, then retries the lookup
once. The Shell's loader (`createShellCommandBus`) is backed by `MicroAppManager`: it returns
`'not_registered'` for an unknown slug, otherwise `ensureLoaded(slug)` downloads + `init`s the
bundle (subscribing its handlers) and returns `'loaded'`. Concurrent loads of the same module
share one in-flight promise. **Net effect: a caller can publish `drive.*` without knowing whether
the drive module is loaded.**

### 3.6 Shell-owned commands

Registered once when the bus is created (`registerShellCommands`):

| Command | Owner | Purpose |
| --- | --- | --- |
| `shell.layout.register_menu` / `unregister_menu` | `libs/shell/src/menu` | Command-bus facade over the host `IMenuRegistry`, for **out-of-repo bundles handed only a bus**. In-repo modules should call `host.menuRegistry.register(...)` directly — it is typed, synchronous and throws at the call site on conflict. Both paths hit the same registry. |
| `core.dynamic_model.get_schema` | `libs/common/src/dynamicModel` | Resolves a `SchemaPack` by schema name, decoupling consumers from the concrete `schemaRegistry`. Returns a live, non-serializable object. |
| `shell.erp_modules.list_all` / `search` | `libs/shell/src/erpModules` | Queries about registered ERP modules. |
| `shell.routing.get_active_context` / `navigate` / `navigate_will_return` / `navigate_return_to` | `libs/shell/src/routing` | Current path, `returnTo`, active org and module **slugs**; and navigation intents. |
| `shell.session.is_authenticated` / `get_expires_at` | `libs/shell/src/authenticate` | Session state. |
| `shell.user_context.get` / `get_active_org` / `get_local_settings` / `set_local_settings` | `libs/shell/src/userContext` | The signed-in user, their organizations, and theme/language settings. |
| `shell.shared_state.get_current_org_id` / `get_current_module` | `modules/shell/src/features/sharedState` | The current org **id** and module slug. See 3.7. |

#### Adding commands owned by a Shell implementation

`registerShellCommands` lives in `libs/shell`, which is consumed by `modules/shell` and **never
the reverse** — so it cannot import a concrete Shell's services to register them. A Shell passes
its own registrars in instead, through an optional prop threaded down the existing chain
(`ShellProviders` → `MicroAppHostProvider` → `createShellCommandBus`):

```tsx
// nikkierp/modules/shell/src/index.tsx
const shellCommandRegistrars = [registerSharedStateCommands];

<ShellProviders microApps={microApps} envVars={…} extraRegistrars={shellCommandRegistrars}>
```

```ts
// libs/shell/src/commandBus/registerShellCommands.ts
export type ShellCommandRegistrar = (bus: ICommandBus) => () => void;
export type ShellCommandDeps = {
    menuRegistry: IMenuRegistry,
    extraRegistrars?: ShellCommandRegistrar[],
};
```

They subscribe in the **same synchronous pass** as the built-ins, so there is no window in which a
component could publish before the handler exists. A registrar keeps the standard contract: it
returns a single teardown closure. Two other things fall out of this arrangement, both load-bearing:

- The command's first segment must stay **`shell`** — the bus hands segment 0 to its `ModuleLoader`,
  so any other prefix would be treated as a lazily-loadable micro-app slug.
- Listing the registrar is also what **imports the service module**, and `@storeService` builds its
  slice on first instantiation (i.e. at import). That is what guarantees the slice exists before
  anything reads it.

### 3.7 Shell shared state: the current org and module

Feature modules routinely need to know *which organization the user is working in* — most backend
resources are org-scoped, and a request that omits the org id is filtered to nothing rather than
to everything. `SharedStateService`
(`nikkierp/modules/shell/src/features/sharedState/`) is the single authoritative answer.

**Why it is not `shell.routing`.** The routing slice holds the org and module **slugs** taken from
the URL. An API call needs the org **id**, and resolving slug → id requires the org list from
`v1/iam/me/context`, which arrives asynchronously. `SharedStateService` is where that resolved id
lands, so a caller neither redoes the lookup nor waits for it on every request.

**Writing it — Shell only.** The commands are deliberately **read-only**: letting a micro-app set
the active org over the bus would let one module silently change what every other module reads.
The Shell writes it from two places:

- **On switch** — `OrgSwitchDropdown` / `ModuleSwitchDropdown` set the value *before* navigating,
  because the new route's data fetches start as soon as it renders.
- **On hard reload** — the dropdowns never run, so `OrgSubLayout` / `ModuleSubLayout` re-derive it
  from the URL. `OrgSubLayout` keys its effect on the resolved `found?.id` so it re-runs when the
  `me/context` fetch lands, which on a cold load has usually not resolved by the first render.

Setters are `@storeSyncMethod`s, so they must be **dispatched** (`useServiceLayer` in React,
`dispatchServiceMethod` outside it) — calling them directly runs the body and writes nothing to the
slice. See 3.2.

**Reading it from a module.** Publish the command; do not reach into the Shell store, which sits on
a separate `ModuleStoreContext` a micro-app cannot select from.

```ts
// coremart/modules/vendingMachine/src/common/orgContext.ts
export async function getCurrentOrgId(): Promise<string | null> {
    const bus = CommandBus.instance;
    if (!bus) throw new Error('CommandBus is not initialized');
    const response = await bus.publish<string | null>({ name: 'shell.shared_state.get_current_org_id' });
    return response.result?.data ?? null;
}
```

The command name is a literal rather than an import: the Shell owns the name, and a module must not
take a compile-time dependency on a specific Shell implementation to read it.

**Do not cache the result.** The user can switch orgs at any moment, and a stale id silently returns
another organization's rows — a wrong answer that looks like a correct one. The accessor is async
because the bus is; that is the cost of the boundary, and it is cheap next to the request it
precedes.

A module that scopes *every* read this way should do it once in a base service rather than in each
hook — `OrgScopedCrudService` in `coremart/modules/vendingMachine/src/common/service/` overrides
`search` / `getById` to fold the org id in, which is why no list hook in that module mentions it.
Note that `RestApi.search` includes `org_id` in its de-duplication key: without that, two orgs
requesting the same page would share one in-flight promise and whichever asked first would answer
for both.

### 3.8 Menus

A module contributes its menu in `init` via `host.menuRegistry.register(buildXMenu(slug))`.
Contributions are keyed by slug, so modules cannot clobber each other; re-registering a slug
throws unless `{ override: true }`. Registration is **permanent** — `initPack` caches `init` per
slug, so unregistering on unmount would make re-registration impossible.

Items carry **i18n keys, not labels** (`labelKey`), plus a `translationNs` on the contribution:
`init` runs outside React and possibly before the namespace loads, so the Shell's `MenuBar`
translates at render time. Key style differs per module (`iam` uses `menu.users`;
`drive` / `inventory` use `menu_overview`) — the source of truth is
`backend/nikkierp/modules/essential/infra/langJson/{locale}/{module}.json`.

### 3.9 Enforced boundaries

`eslint.config.mjs` encodes the architecture as lint zones; a violation fails the build. Do not
work around them:

- `libs/viewengine` may not import any kit, `@nikkierp/ui`, the shell or any module.
- `libs/ui` may not import a view kit (kits depend on ui, never the reverse) and may not import
  the `@nikkierp/viewengine/engine` barrel (it exposes `defaultViewEngine`) — use `./core`,
  `./metadata` or `./render`.
- Modules may not import `@nikkierp/microapp-*` / `@coremart/microapp-*`.
