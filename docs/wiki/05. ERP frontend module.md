# ERP frontend module

A **frontend module** is a micro-app: a self-contained bundle that the Shell lazily loads,
mounts as a custom element, and hands a set of host-owned services. This document describes the
anatomy of one — its contract, its folders, and how each piece of a resource is wired — using
`nikkierp/modules/identity` and its `user` resource as the worked example.

Doc [01. Micro Frontend architecture](<01. Micro Frontend architecture.md>) covers the Shell
side of the boundary (lifecycle, command bus, host services). This document covers the module
side.

## 1. What a module is

A module is a pnpm workspace package under `{app}/modules/{name}/` that builds to a single ES
bundle. The host app declares it in `src/main.tsx` as `MicroAppMetadata`:

| Field | Meaning |
|---|---|
| `slug` | The module's identity. **Must equal the backend ERP module name** — it is the command-name prefix, the i18n namespace, and the menu registry key. |
| `basePath` | URL segment the Shell mounts it under. |
| `htmlTag` | Custom element name the bundle defines. |
| `bundleUrl` / `configUrl` | Where the Shell fetches it from (remote/out-of-repo apps only). |
| `dependsOn` | Other micro-apps that must be loaded first. |

Note the frontend package is `identity` while its slug is `iam` — the folder rename is pending.
Everything that crosses a boundary uses `iam`.

## 2. The bundle contract

The entry point default-exports a `MicroAppBundle`. Its `init` is the module's one chance to
register everything the Shell and the command bus may need before the module is ever displayed.
`nikkierp/modules/identity/src/index.tsx` in full:

```tsx
const bundle: MicroAppBundle = {
	init({ htmlTag, slug, host }) {
		const domType = MicroAppDomType.SHARED;
		defineWebComponent(Main, { htmlTag, domType });

		// No `registerReducer`: identity keeps its state in its own store (`./store`), and
		// reaches the Shell only through the command and event buses.
		registerModelSchemas();
		// IAM-specific templates go onto the host-owned engine, never a new instance.
		contributeIdentityViewKit(host.viewEngine);
		host.menuRegistry.register(buildIdentityMenu(slug));
		registerUserCommands(host.commandBus);
		registerGroupCommands(host.commandBus);
		registerOrganizationCommands(host.commandBus);
		registerRoleCommands(host.commandBus);

		return { domType };
	},
};

export default bundle;
```

The five steps, in order:

1. **`defineWebComponent`** — register the custom element. `MicroAppDomType.SHARED` renders into
   the Light DOM and shares the host's styles; `ISOLATED` uses a Shadow DOM and its own
   `RequestMaker`.
2. **Model schemas** — tell the shared `schemaRegistry` which backend resource path serves each
   dynamic-model schema.
3. **View kit** — contribute this module's templates onto `host.viewEngine`. Use the host's
   engine; never construct one and never import `defaultViewEngine`.
4. **Menu** — `host.menuRegistry.register(buildXMenu(slug))`.
5. **Commands** — subscribe the module's non-CRUD command handlers.

Three rules govern `init`:

- **It runs once per slug, outside React, possibly before the module is displayed.** So it must
  be synchronous for anything the bus or the menu bar depends on, and must not assume a DOM or a
  loaded i18n namespace.
- **Use the host's services.** `host.commandBus`, `host.viewEngine`, `host.menuRegistry` are
  created once by the Shell. A module that builds its own is invisible to everyone else.
- **Register commands here, never in a `useEffect`.** The bus resolves a command by lazily
  loading the owning module and calling its `init`; a handler subscribed at render time does not
  exist yet when that happens.

`registerReducer` is available but **identity does not use it** — the module owns a private
store instead (§4). Pages are assembled in React, not in `init`:

```tsx
function MicroAppInner(props: MicroAppProps): React.ReactNode {
	const pages = React.useMemo(() => [
		...buildUserPages(), ...buildGroupPages(), ...buildOrganizationPages(),
		...buildRolePages(), ...buildRoleAssignmentPages(),
	], []);

	return <ViewEngineRouter microAppProps={props} engineProps={{ pages, indexElement: <h1>Identity</h1> }} />;
}
```

## 3. Module anatomy

```
nikkierp/modules/identity/
├── package.json              # @nikkierp/microapp-identity; exports "." → ./src/index.tsx
├── vite.config.ts            # build.lib entry = src/index.tsx, formats ['es']
└── src/
    ├── index.tsx             # ← the MicroAppBundle default export
    ├── menu.ts               # ← menu contribution
    ├── store.ts              # ← this module's private Redux store
    ├── constants/index.ts    # module slug + schema-name constants
    ├── features/
    │   ├── user/             # ← one folder per resource
    │   │   ├── userService.ts    # HTTP + store slice
    │   │   ├── commands.ts       # command names + bus subscriptions
    │   │   ├── types.ts          # request/response types
    │   │   └── index.ts          # barrel
    │   ├── group/  organization/  role/
    │   ├── http.ts
    │   └── roleAssignment.ts
    ├── pages/                # view-engine page metadata — user.ts, group.ts, role.ts, …
    ├── schemas/              # static schema JSON fallbacks
    ├── viewkit/              # module-owned view kit: ids.ts, kit.ts, props.ts, components/, pages/
    └── hooks/
```

Two things to know before reading the tree:

- **`pages/*.ts` are metadata, not components.** `pages/user/UserListPage.tsx`,
  `pages/user/UserFormPage.tsx` and `pages/overview/OverviewPage.tsx` still exist but are
  **entirely commented out** — dead legacy JSX. The live users page is `pages/user.ts`.
- **A module never imports another module.** Cross-module calls go over the command bus; the
  eslint config fails the build on `@nikkierp/microapp-*` / `@coremart/microapp-*` imports from a
  module.

## 4. Case study — the `user` resource

Five small files, each with one job.

### 4.1 Constants — the contract with the backend

```ts
// src/constants/index.ts
export const IAM_MODULE = 'iam';

export const GROUP_SCHEMA_NAME = 'iam_group';
export const USER_SCHEMA_NAME = 'iam_user';
// These must match the backend Go constants verbatim — `SchemaRegistry` rejects a schema whose
// response name differs, which leaves the page loading forever.
export const ORGANIZATION_SCHEMA_NAME = 'iam_org';
export const ORG_UNIT_SCHEMA_NAME = 'iam_orgunit';
export const ROLE_SCHEMA_NAME = 'iam_role';
```

Schema names are `{module}_{entity}` in snake_case, never dotted, and are declared as
`XSchemaName` in `backend-coremart26-mono/nikkierp/modules/{module}/domain/models/{entity}.go`.
Read the Go constant rather than guessing from the resource path — `iam_org`, not
`iam_organization`.

### 4.2 The store and the service

The module owns a private Redux store, created at module scope:

```ts
// src/store.ts
/**
 * Created at module scope because `@storeService` runs at import time, before `init()`.
 * This module must not import the services — they import this.
 *
 * The Shell cannot read this store and neither can a sibling micro-app: anything that
 * has to cross that boundary goes through the command bus or the event bus.
 */
export const identityStore = createModuleStore('identity');
```

The whole user CRUD surface is then 19 lines, because `StoreCrudServiceBase` supplies every
operation and `@storeService` turns them into a Redux slice (§5):

```ts
// src/features/user/userService.ts
@storeService('UserService', identityStore)
export class UserService extends StoreCrudServiceBase {
	public constructor() {
		super({ moduleName: IAM_MODULE, schemaName: USER_SCHEMA_NAME });
	}
}

export const userService = new UserService();
```

### 4.3 Commands — generated CRUD, hand-written exceptions

The module subscribes **none** of the CRUD commands. `resourceCommands(schemaName)` generates
their names, and the Shell's single `core.resource.*` prefix subscription serves them by
delegating to whatever service the schema registered:

```ts
// src/features/user/commands.ts
const PREFIX = `${IAM_MODULE}.${USER_SCHEMA_NAME}`;   // "iam.iam_user"

export const UserCommands = Object.freeze({
	...resourceCommands(USER_SCHEMA_NAME),
	ACTIVATE: `${PREFIX}.activate_user`,
	INVITE: `${PREFIX}.invite_user`,
	SUSPEND: `${PREFIX}.suspend_user`,
	MANAGE_ROLE_ASSIGNMENTS: `${PREFIX}.manage_user_role_assignments`,
	SEARCH_ASSIGNED_ROLES: `${PREFIX}.search_user_assigned_roles`,
} as const);

export function registerUserCommands(bus: ICommandBus): () => void {
	registerSchemaModule(USER_SCHEMA_NAME, IAM_MODULE);   // schema → owning module
	registerCrudService(USER_SCHEMA_NAME, userService);   // schema → the service CRUD delegates to

	const unsubscribers = [
		bus.subscribe(UserCommands.ACTIVATE, cmd => setStatus('activate', cmd)),
		bus.subscribe(UserCommands.INVITE, cmd => setStatus('invite', cmd)),
		bus.subscribe(UserCommands.SUSPEND, cmd => setStatus('suspend', cmd)),
		bus.subscribe(UserCommands.SEARCH_ASSIGNED_ROLES, cmd => ra.searchAssignedRoles('users', payload(cmd))),
		bus.subscribe(UserCommands.MANAGE_ROLE_ASSIGNMENTS, cmd => ra.manageRoleAssignments('users', payload(cmd))),
	];
	return () => unsubscribers.forEach(unsubscribe => unsubscribe());
}
```

Command names are `{module}.{schema}.{action}`. The two registry calls come **first** — the
generic CRUD path cannot serve `iam_user` until it knows which module owns the schema and which
service to call.

Subscribe a dedicated command only when the operation is genuinely not CRUD over the schema:
`SEARCH_ASSIGNED_ROLES` and `MANAGE_ROLE_ASSIGNMENTS` hit endpoints the dynamic schema cannot
express, and `ACTIVATE` / `INVITE` / `SUSPEND` are `update` carrying a fixed `status` — they need
their own names because the detail template's contextual actions send only `{id, etag}`, so the
status value has nowhere else to travel.

### 4.4 The page — JSON metadata, not JSX

`pages/user.ts` imports only from `@nikkierp/viewengine/metadata` and
`@nikkierp/viewkit-mantine/props`. No React, no Mantine, no module components — everything the
page shows is named by id, key or command:

```ts
export function buildUserPages(): PageNode[] {
	const splitView = resourceSplitViewProps({
		primary: buildUserListProps(),
		secondary: buildUserDetailProps(),
	});

	return [definePage({ routePath: 'users', template: splitView.template, props: splitView.props })];
}
```

The list binds actions to command names and labels to i18n keys:

```ts
resourceListProps({
	schemaName: c.USER_SCHEMA_NAME,
	translationNs: c.IAM_MODULE,
	linkField: 'id',
	searchCommand: UserCommands.SEARCH,
	createEnabled: true,
	deleteCommand: UserCommands.DELETE,
	archiveCommand: UserCommands.SET_IS_ARCHIVED,
	updateSaveCommand: UserCommands.UPDATE,
	extraActions: [
		{ label: 'action.suspend', command: UserCommands.SUSPEND, supportMultiple: true, requireSelection: true },
	],
	fieldRenderers: {
		avatar_url: { renderer: 'avatar' },
		status: { renderer: 'badge', prefix: 'status.', colorMap: { active: 'green', invited: 'indigo' } },
	},
})
```

The detail binds titles and status to schema fields, and contextual actions to commands guarded
by a condition:

```ts
resourceDetailProps({
	schemaName: c.USER_SCHEMA_NAME,
	translationNs: c.IAM_MODULE,
	titleLvl1: { schemaField: 'display_name' },
	titleLvl2: { schemaField: 'email' },
	allStatuses: [{ value: 'active', label: 'status.active', color: 'green' }, /* … */],
	currentStatus: { schemaField: 'status' },
	standardActionCommands: {
		getById: UserCommands.GET_BY_ID, create: UserCommands.CREATE, update: UserCommands.UPDATE,
		delete: UserCommands.DELETE, archive: UserCommands.SET_IS_ARCHIVED,
	},
	contextualActions: {
		suspend: {
			label: 'action.suspend', command: UserCommands.SUSPEND,
			condition: { field: 'status', operator: 'equal', value: 'active' },
		},
	},
	formSections: [{ header: 'form.generalInformation', fields: ['display_name', 'email'] }],
	childrenNodes: [buildAssignedRolesSection()],
})
```

`childrenNodes` render after the form, **only in update mode** — during create there is no record
id to filter related records by. Wrap each in `collapsibleSectionNode` and embed a related-records
table with `resourceTableNode`, whose `filterGraph` interpolates the current route param:

```ts
collapsibleSectionNode(
	{ header: 'user_sections_assignedRoles', translationNs: c.IAM_MODULE },
	[resourceTableNode({
		schemaName: c.ROLE_SCHEMA_NAME,
		translationNs: c.IAM_MODULE,
		searchCommand: RoleCommands.SEARCH,
		filterGraph: { if: ['assigned_users', 'linked', '${id}'] },   // `linked` filters across a many edge
		linkField: 'id',
		linkRoutePath: 'roles',                                       // rows point at a *different* page
		extraActions: [{ label: 'assignment.manageRoles', routePath: 'roles' }],
	})],
)
```

For templates, renderers, contribution ids and the render pipeline, see doc
[03. View engine](<03. View engine.md>) §4.6.

### 4.5 The menu

```ts
// src/menu.ts
/**
 * Menu entries carry i18n keys, not labels: the contribution is registered from the
 * bundle's `init`, which runs outside React and possibly before the namespace loads.
 * The Shell resolves them against `translationNs` at render time.
 */
const ITEMS: MenuItem[] = [
	{ labelKey: 'menu.overview', link: '/overview' },
	{ labelKey: 'menu.users', items: [
		{ labelKey: 'menu.users', link: '/users' },
		{ labelKey: 'menu.groups', link: '/groups' },
	] },
];

export function buildIdentityMenu(slug: string): MenuContribution {
	return { slug, translationNs: IAM_MODULE, items: ITEMS };
}
```

Contributions are keyed by slug, so modules cannot clobber each other; re-registering a slug
throws unless `{ override: true }` is passed. Registration is **permanent** — `initPack` caches
`init` per slug, so unregistering on unmount would make re-registration impossible.

## 5. The `storeService` decorator pattern

A module's state is private. `createModuleStore(name)` gives it its own Redux store that the
Shell cannot read and no sibling micro-app can reach; anything that has to cross that boundary
goes over the command bus or the event bus.

`@storeService` is what connects a plain service class to that store. It is defined in
`nikkierp/libs/ui/src/appState/decorators.ts` and imported from `@nikkierp/ui/appState/store`.

### 5.1 What it does

> Turns a service class into a Redux slice named `sliceName` on `moduleStore`. Every method
> found on the prototype chain — including those inherited from a base class such as
> `CrudServiceBase` — becomes a thunk plus the reducer cases maintaining `state[methodName]`.

`sliceName` is passed explicitly rather than read off `ServiceClass.name`, because a minifier
renames the class and two services collapsing to one mangled name would silently share a slice.
`createModuleStore` throws on a duplicate slice name rather than letting that happen quietly.

The slice is built on the **first instantiation**, not at class-definition time, because the
generated thunks call their methods on a real instance. Services are module-scope singletons
(`export const userService = new UserService()`), so in practice that is still import time —
which is why `store.ts` must be created at module scope, before any service imports it.

### 5.2 The critical caveat: installed methods do not dispatch

> **The installed methods do not dispatch.** What lands on the instance is a *bound copy of the
> plain method* with its thunk attached as metadata, so `userService.getById(...)` runs the body
> and returns the right data while writing nothing to the store.

To have a call recorded in the slice, go through `useServiceLayer` in React or
`dispatchServiceMethod` anywhere else — including from inside another service method, where
`this.otherMethod()` is likewise just a direct call.

This is deliberate: a command-bus handler wants the data and no store write, while a component
wants the loading/error state. The same method serves both.

### 5.3 The three method kinds

`SharedStateService` in `nikkierp/modules/shell/src/features/sharedState/sharedStateService.ts`
is the clearest illustration, because it uses all three in one class:

```ts
@storeService(SLICE_NAME, shellStore, { initialState: buildInitialState() })
export class SharedStateService {
	@storeSyncMethod
	public setCurrentOrgId(orgId: string | null | undefined): string | null {
		return orgId ?? null;
	}

	@storeSyncMethod
	public setCurrentModule(moduleSlug: string | null | undefined): string | null {
		return moduleSlug ?? null;
	}

	/**
	 * Reads the slice directly rather than through a selector, for command-bus callers that
	 * have no React context to select from.
	 */
	public getCurrentOrgId(): string | null {
		return this.readState()?.setCurrentOrgId ?? null;
	}

	private readState(): SharedState | undefined {
		return (shellStore.getState() as Record<string, SharedState | undefined>)[SLICE_NAME];
	}
}

export const sharedStateService = new SharedStateService();
```

| Annotation | Becomes | State it maintains |
|---|---|---|
| `@storeAsyncMethod` | A `createAsyncThunk` with pending/fulfilled/rejected cases | `state[methodName]` = `{ status, data, clientErrors, error, doneAt }` |
| `@storeSyncMethod` | A plain reducer case | `state[methodName]` = the method's return value, replaced wholesale. No promise, no envelope. |
| *(none)* | Nothing | Invisible to the store — an ordinary helper |

Note the state keys are the **method names**, which is why the getters above read
`state.setCurrentOrgId`. `StoreCrudServiceBase` arrives pre-annotated, so a CRUD service like
`UserService` declares no methods and still gets the full set.

`collectMethodKinds` walks the prototype chain prototype-first, so a subclass override wins over
the base's annotation, and reads property *descriptors* rather than indexing — indexing would
invoke a getter.

### 5.4 Mechanics worth knowing

- **`STORE_METHOD_TAG`** (a `Symbol.for`) is attached to each bound method, carrying
  `{ methodName, sliceName, moduleName, thunk | syncAction }`. It is what lets
  `useServiceLayer(userService.getById, params)` resolve a *bare function reference* back to its
  slice — two services inheriting `getById` share one prototype function object, so the reference
  alone could not say which slice it belongs to. Binding also preserves `this` for `#private`
  field reads.
- **The decorator returns a subclass**, not the original class. A TC39 class decorator's
  `addInitializer` runs with `this` bound to the constructor rather than an instance, so
  subclassing is the only hook that sees each instance after its fields are set.
- **Errors surface at import.** A blank slice name throws at decoration time rather than on first
  use.

## 6. Translation keys

**Every displayed label is an i18n key, never literal text.** Menu items carry `labelKey`; page
metadata carries `translationNs` plus keys like `action.suspend`, `status.active`,
`form.generalInformation`; the badge renderer's `prefix: 'status.'` prepends a namespace segment
to a raw enum value. Kit components resolve them at render time via
`useTranslate(params.translationNs)`, and `translationNs` is a required prop on every resource
template.

### The namespace is the backend module name

The i18next HTTP backend's `loadPath` *is* the mapping:

```ts
loadPath(lngs, namespaces) {
	return `v1/essential/languages/json?language_code=${lngs[0]}&module_name=${namespaces[0]}`;
},
```

So the i18next namespace ≡ the backend module name, which is why `translationNs: IAM_MODULE`
(`'iam'`) is correct and why the module slug must match the backend module name (§1).

### Source of truth

Keys live in the backend, not the frontend:

```
backend-coremart26-mono/nikkierp/modules/essential/infra/langJson/
├── en-US/{common,drive,essential,iam,inventory}.json
└── vi-VN/{common,drive,essential,iam,inventory}.json
```

Adding a label means adding the key to `{locale}/{module}.json` **for every locale**, then
referencing it from the frontend. Schema field labels take the same path from the other
direction: the model schema returns a `nikkiLangJson` per field, which is either an inline
per-locale map or a `{"$ref": "some.key"}` pointing into the same files, resolved by
`useLocalize`.

Two rules that follow:

- **There is no fallback language** — `fallbackLng` is deliberately commented out so a missing
  translation renders as the raw `namespace:some.key` and gets noticed. Do not add one.
- **Modules must not ship their own bundles.** `registerMicroAppI18nResources` is
  `@deprecated — Use HttpBackend instead`.

Key style is not uniform across modules: `iam` uses dotted (`menu.users`), `drive` and
`inventory` use underscored (`menu_overview`), and `pages/user.ts` mixes both
(`user_sections_assignedRoles`). Follow the existing style of the module you are writing for —
the backend JSON file is the arbiter.

## 7. `data-testid` on interactive elements

Every interactive element a user can act on — buttons, inputs, selects, checkboxes, links, menu
items, tabs, clickable rows, pagination controls, modal action buttons — carries a
`data-testid`, so end-to-end automation has a selector that does not depend on a translated
label.

```
data-testid="{module}.{component}.{element}"
```

Segments are **camelCase, joined by dots**, matching the contribution-id style
(`nikkierp.mantine.components.pageHeader.v1`) and the repo's strict-camelCase rule. There is no
version suffix — test ids are not versioned contracts.

- **`{module}`** — the micro-app slug: `shell`, `identity`, `authorize`, `drive`, `inventory`,
  `vendingMachine`. Shared libraries with no consumer prefix fall back to `ui`.
- **`{component}`** — the component or page region (`userList`, `kioskDisplaySettings`).
- **`{element}`** — what it is (`create`, `search`, `submit`).

```html
<button data-testid="identity.userList.action.create">…</button>
<input  data-testid="vendingMachine.kioskList.filterStatus" />
```

This is the fourth member of the self-describing-DOM family. The view engine's
`data-component` / `data-page` / `data-command` (`libs/viewengine/src/core/domAttributes.ts`)
name the *subtree* that produced an element; `data-testid` names the individual **leaf** a test
clicks or types into.

### 7.1 The helper

`testAttrs` and `joinTestId` live in `@nikkierp/common/utils` — `libs/common` is framework-free
and sits below every eslint boundary zone, so the engine, `libs/ui`, view kits and modules in
both products can all import them:

```ts
import { joinTestId, testAttrs } from '@nikkierp/common/utils';

<Button {...testAttrs('identity', 'userList', 'action', 'create')}>…</Button>
```

`testAttrs` **emits nothing when the id is empty**, so an element whose prefix has not been
threaded yet carries no misleading blank attribute — the same contract as `commandAttrs`.
`joinTestId` skips empty segments, so an optional prefix or discriminator needs no branching.

`TestIdProps` (`{ testId?: string }`) is the prop type to mix into a component that lets its
consumer namespace the ids it emits.

### 7.2 Repeated and dynamic elements

Append a **stable** discriminator: a record id, field name, action command or option value.

```
identity.userList.row.01H8XYZ…
vendingMachine.kioskList.action.create
```

**Never an array index** for a list that can be sorted, filtered or reordered — a test's handle
must survive those. An index is a documented last resort only when a record has no id, which is
exactly what `rowTestIdOf` in `DataTable/testIds.ts` implements.

### 7.3 Threading a prefix through shared components

Shared components take an optional `testId` prefix (`{module}.{component}`) and append their own
`.{element}` segments. When no prefix is passed they **derive** one from what they already know
(`tableName`, `schemaName`, field `name`, `command`), so call sites that have not been threaded
yet still emit stable ids.

`DataTable` is the reference — one `testId` prop namespaces its whole surface, and
`DataTable/testIds.ts` derives the rest:

```ts
const ids = dataTableTestIds(testId, tableName);   // prefix falls back to `ui.{tableName}`

ids.search()            // {prefix}.search
ids.action(action)      // {prefix}.action.{testId ?? command ?? label}
ids.sort(field)         // {prefix}.sort.{field}
ids.row(rowId)          // {prefix}.row.{recordId}
ids.rowCell(rowId, f)   // {prefix}.row.{recordId}.cell.{field}
ids.settingsApply()     // {prefix}.settings.apply
```

Instrumenting a central component covers its consumers at once: every table toolbar action, every
`AutoField` form input and every `ConfirmModal` inherits ids without the call site being touched.

A component that can appear **twice on one page with no derivable identity** takes a *required*
`testId` prefix instead, and the parent bakes in the distinguishing detail — e.g. the two
`MediaPlaylistSelect` in `KioskDisplaySettings.tsx` become
`vendingMachine.kioskDisplaySettings.playlistWaiting` and `…playlistShopping`.

### 7.4 In metadata-driven pages

The view-kit props schemas are `.strict()`, so a page may only pass `testId` once the schema
accepts it. When it is absent the renderer derives the prefix from the module slug and schema
name (`identity.userList`), which means identity's pages need no authoring to get ids.
`ComponentAnchor` / `PageAnchor` stay untouched: attaching attributes remains each renderer's own
job, per the philosophy documented in `domAttributes.ts`.

### 7.5 Verifying

On an affected page, in DevTools:

```js
const ids = [...document.querySelectorAll('[data-testid]')].map(e => e.dataset.testid);
console.log(ids.length, new Set(ids).size);   // counts must match → all ids unique
```

Every visible interactable should appear in that list. A lint guard (`no-restricted-syntax`)
warns on a `Button` / `ActionIcon` / `Anchor` / `Menu.Item` / `Tabs.Tab` carrying neither
`data-testid` nor `testId`, promoted to an error per module as its sweep lands.

The rollout plan and its per-module task breakdown are in
[`ai-prompts/testid/01-plans.md`](../ai-prompts/testid/01-plans.md).

## 8. Creating a new module — checklist

1. **Scaffold the package.** Copy the tsconfig samples from `nikkierp/scaffold/`. `package.json`
   exports `"." → ./src/index.tsx`; `vite.config.ts` sets `build.lib.entry` to the same file with
   `formats: ['es']`; list `**/*.css` in `sideEffects`.
2. **`src/constants/index.ts`** — the module slug (matching the backend module name) and one
   `X_SCHEMA_NAME` per resource, copied verbatim from the backend Go constants.
3. **`src/store.ts`** — `createModuleStore('{name}')` at module scope.
4. **Per resource, `src/features/{resource}/`** — `xService.ts` (`@storeService` +
   `StoreCrudServiceBase`), `commands.ts` (`resourceCommands` spread + custom names +
   `registerSchemaModule` / `registerCrudService` + subscriptions), `types.ts`, `index.ts`.
5. **`src/pages/{resource}.ts`** — page metadata via `definePage` and the `*Props` builders.
   Never JSX.
6. **`src/menu.ts`** — `buildXMenu(slug)` returning a `MenuContribution` of `labelKey` items.
7. **`src/index.tsx`** — the `MicroAppBundle` default export following §2's five steps.
8. **Register with the host** — add a `MicroAppMetadata` entry to the app's `src/main.tsx`, and
   give the package a `dev` script with an unused `NIKKI_BFF_HTTP_PORT`.
9. **Translation keys** — add `{module}.json` for every locale under the backend's
   `essential/infra/langJson/`.
10. **`data-testid`** on every interactive element (§7): spread
    `testAttrs('{module}', '{component}', '{element}')` from `@nikkierp/common/utils`, and pass a
    `testId` prefix to shared components (`DataTable`, `AutoField` forms, `ConfirmModal`) rather
    than tagging their internals.
